How to Convert an LLM Project Idea into GPU Requirements

Daya Shankar
August 5, 2026
6 min read

“Our team wants to build an AI assistant” is not enough information to choose a GPU.

Before comparing L4, L40S, A100 or H100 instances, convert the idea into measurable requirements:

  • Which model will run?
  • Is the workload inference, RAG or fine-tuning?
  • How long are the prompts?
  • How many people will use it?
  • How quickly must it respond?

You do not need perfect estimates. You need enough information to shortlist a GPU and run a realistic test.

Turn the Idea into a Specific Workload

Start by completing this sentence:

We want to use [model] to perform [task] for [number of users], with responses delivered within [latency target].

For example:

We want to use a 7B instruction model to answer questions from internal documents for 20 employees, with the first response appearing within three seconds.

That single sentence already tells you more than “we need a GPU for RAG.”

Record these details:

QuestionExample answer
What will the model do?Answer questions from documents
Which model will you test?A 7B instruction model
What is the workload?RAG inference
How many users?20 employees
Expected simultaneous users?3–5
Maximum prompt length?8,000 tokens
Required response speed?First token within 3 seconds
Will the model be fine-tuned?Not initially

Hugging Face provides an accelerate estimate-memory command and an online estimator for checking model size across different data types before loading it.

Leave Room Beyond the Model Weights

Do not choose a 16GB GPU simply because your calculation says the weights need 14GB.

Inference also requires memory for:

  • The inference framework
  • Temporary calculations
  • Input and output tensors
  • The KV cache
  • Concurrent requests
  • Longer context windows

The KV cache stores information from previously processed tokens. Longer prompts and more simultaneous sequences therefore reduce the number of requests a GPU can serve. vLLM calculates available concurrency partly from KV-cache capacity and maximum model length.

As a starting point, avoid planning to use every gigabyte of VRAM. Leave headroom and measure peak memory under realistic traffic.

Add Context Length and Concurrency

Two applications using the same model may need different GPUs. For example, latency-sensitive applications such as AI voice agents, conversational assistants, live translation, and real-time copilots may require faster inference and greater concurrency than an internal chatbot using the same underlying model.

Application A

  • One user
  • 2,000-token prompts
  • One request at a time
  • Quantized model

Application B

  • Twenty users
  • 16,000-token prompts
  • Five concurrent requests
  • Higher-precision model

Application B needs substantially more memory and throughput, even though both use the same base model.

Estimate:

  • Average input tokens
  • Maximum input tokens
  • Average output tokens
  • Expected simultaneous requests
  • Peak requests per minute

Do not use the model’s maximum supported context length automatically. Set the application limit to what users genuinely need.

Decide Whether You Need Inference or Fine-Tuning

For Inference

You mainly need memory for:

  • Model weights
  • KV cache
  • Inference overhead
  • Active requests

Quantization can often make inference possible on a smaller GPU.

For Fine-Tuning

You may also need memory for:

  • Gradients
  • Optimizer states
  • Activations
  • Training batches
  • Temporary buffers

Training memory can be many times larger than the model weights alone. Batch size, sequence length, model architecture and training method all affect the result.

LoRA or QLoRA may reduce the requirement compared with full fine-tuning, but you should size the GPU using the actual training configuration rather than an inference estimate.

Convert the Requirements into a GPU Shortlist

Use VRAM to create the initial shortlist.

Estimated requirementGPU capacity to test first
Under 12GBExisting local GPU or entry-level cloud GPU
12–20GB16GB or 24GB GPU
20–40GB24GB or 48GB GPU
40–70GB48GB or 80GB GPU
Above 70GB80GB+ GPU or multi-GPU setup

These are testing ranges, not guaranteed recommendations.

Choose the next capacity tier when:

  • The estimate is close to the GPU limit
  • You expect longer contexts later
  • Several requests will run together
  • You need space for multiple models
  • The project will move from testing to production

Do not choose by VRAM alone. Memory bandwidth and compute performance can affect token generation speed, while CPU, RAM and storage can affect model loading and data preparation.

Size the Rest of the Instance

A GPU VM also needs enough surrounding resources.

System RAM

Keep enough RAM for:

  • Loading model files
  • Tokenization
  • Document processing
  • Vector-search components
  • CPU offloading
  • Application services

Storage

Include space for:

  • Model checkpoints
  • Quantized versions
  • Embedding models
  • Datasets
  • Vector indexes
  • Container images
  • Logs

A model repository may contain several files or weight formats, so allocate more storage than the final loaded model size.

CPU

CPU capacity matters for:

  • Tokenization
  • Retrieval
  • API processing
  • Data loading
  • Preprocessing
  • Feeding the GPU efficiently

A powerful GPU can still remain underused if the rest of the instance cannot prepare work quickly enough.

Test the Smallest Reasonable Configuration

Your spreadsheet estimate only creates a shortlist. The benchmark makes the decision.

Run the real model with representative prompts and record:

  1. Peak GPU memory
  2. Time to first token
  3. Tokens generated per second
  4. Maximum stable concurrency
  5. End-to-end response time
  6. Error rate
  7. Cost per completed request

Test at least three conditions:

  • Normal request
  • Longest expected prompt
  • Expected peak concurrency

A model that works for one short prompt is not yet production-ready.

Example: Small-Team RAG Assistant

Suppose a team wants:

  • A 7B model
  • INT4 inference
  • An 8,000-token context limit
  • Three concurrent users
  • RAG over internal documents
  • No fine-tuning

The raw model-weight estimate may be below 4GB, but the project also needs memory for the KV cache and serving framework.

A sensible first test would be a 16GB or 24GB GPU rather than selecting the smallest possible instance.

During testing, the team should measure whether:

  • The context fits reliably
  • Three requests can run together
  • The first token arrives quickly enough
  • Retrieval and tokenization keep the GPU supplied
  • Memory remains available during peak usage

If it passes, there is no reason to rent a larger GPU. If concurrency or context causes memory pressure, the team can reduce those limits, use another optimization or test the next VRAM tier.

Build Requirements Before Comparing GPUs

Convert the project idea in this order:

Do not start with the most powerful GPU you can afford.

Start with the smallest configuration likely to meet the requirement, test it with realistic traffic and upgrade only when the measurements show a clear limitation.
